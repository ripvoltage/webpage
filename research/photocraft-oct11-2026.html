SECCIÓN 1: VEREDICTO

El software de edición de imágenes para escritorio representa históricamente una de las categorías de aplicaciones más vulnerables en la informática[cite: 2]. Productos heredados como Adobe Photoshop, GIMP e ImageMagick han acumulado cientos de vulnerabilidades y exposiciones comunes (CVE) críticas que involucran corrupción de memoria, desbordamientos de pila/heap en analizadores de formatos (PSD, TIFF, EXR), desbordamientos de enteros en rutinas de descompresión, secuestro arbitrario de DLL mediante interfaces binarias de complementos antiguas (ej. filtros .8BF) y ejecución remota de código a través de puentes modernos en Electron/webview[cite: 2].

PhotoCraft (storytold/photocraft) es un editor de imágenes por capas nativo y desarrollado desde cero en Rust, diseñado para ofrecer una paridad operativa 1:1 con Photoshop mientras erradica sistemáticamente estas clases de vulnerabilidades desde su diseño[cite: 2].

Evaluación General: La base de código de PhotoCraft exhibe una postura de defensa en profundidad excepcionalmente blindada[cite: 2]. La corrupción de memoria queda matemáticamente eliminada mediante la prohibición de código unsafe a nivel de espacio de trabajo; los analizadores de archivos limitan activamente la asignación de memoria derivada de entradas no confiables y la expansión de descompresión; los complementos de terceros se ejecutan en un entorno aislado (sandbox) WebAssembly con consumo medido de recursos y cero importaciones del sistema huésped; las interfaces de automatización emplean aislamiento del sistema de archivos basado en capacidades (cap-std); y cada comando central se prueba continuamente contra entradas adversarias mediante pruebas de fuzzing diseñadas para evitar fallos[cite: 2].

SECCIÓN 3: AUTOPSIA DEL CÓDIGO FUENTE (PUNTOS FUERTES DE PHOTOCRAFT)

1. Límite contra Bombas de Descompresión (`crates/format/src/zip.rs`)

En muchos editores de imágenes nativos, la lectura de un archivo comprimido o búfer de capa depende de la longitud sin comprimir declarada en un encabezado no confiable para asignar memoria previamente[cite: 2]. Un archivo de 10 KB que declare un tamaño descomprimido de 16 GB causa una falla inmediata por falta de memoria (OOM)[cite: 2]. El decodificador de contenedores de PhotoCraft limita sistemáticamente estas asignaciones: 

// Desde crates/format/src/zip.rs (Líneas 212-221):
let data = match e.method {
    0 => raw.to_vec(),
    8 => {
        // La longitud sin comprimir proviene de un encabezado ZIP no confiable: un
        // archivo pequeño falsificado no debe reservar gigabytes de antemano, por lo que
        // la preasignación se limita (DEFLATE se expande como máximo ~1032x).
        let mut out = Vec::with_capacity(e.uncompressed.min(raw.len().saturating_mul(1032)).min(64 << 20));
        flate2::read::DeflateDecoder::new(raw)
            .take((max as u64).saturating_add(1))
            .read_to_end(&mut out)
            .map_err(|err| FormatError::corrupt(format!("zip entry `{}`: {err}", e.name)))?;
        out
    }
    // ...
};

Por qué es seguro: La capacidad de asignación está estrictamente acotada por el máximo matemático de expansión de DEFLATE (1032×) y con un tope de 64 MiB[cite: 2]. El flujo está limitado físicamente mediante .take(...), garantizando que un flujo manipulado no pueda escribir gigabytes desmedidos en la memoria[cite: 2].

2. Entorno Aislado WebAssembly Sin Importaciones del Sistema (`crates/plugins/src/runtime.rs`)

Los complementos de terceros representan un vector de ataque frecuente[cite: 2]. Adobe Photoshop ejecuta archivos C++ DLL/dylib no administrados con todos los privilegios del usuario[cite: 2]. PhotoCraft reemplaza esto con un entorno de ejecución WebAssembly aislado donde cualquier importación externa está prohibida: 

// Desde crates/plugins/src/runtime.rs (Líneas 131-137):
let module = Module::new(&engine, bytes).map_err(|e| Error::Module(e.to_string()))?;
if let Some(imp) = module.imports().next() {
    return Err(Error::Abi(format!(
        "el módulo importa `{}.{}`, pero los complementos no reciben importaciones del sistema (sin WASI, archivos o red)",
        imp.module(),
        imp.name()
    )));
}

Por qué es seguro: Al rechazar todas las importaciones en el momento de la instanciación, un módulo de complemento compilado no puede realizar llamadas al sistema, acceder al sistema de archivos, abrir sockets de red, consultar variables de entorno o leer la hora del sistema[cite: 2]. Junto con el control del consumo de instrucciones (FUEL_SLICE = 20_000_000) y límites de memoria lineal (512 MiB), los filtros maliciosos o defectuosos no pueden congelar el editor ni vulnerar el sistema huésped[cite: 2].

3. Autenticación de Token en Tiempo Constante (`crates/automation/src/security.rs`)

PhotoCraft admite automatización mediante scripts e integración con agentes a través de un protocolo TCP JSON en bucle local y el Protocolo de Contexto de Modelo (MCP)[cite: 2]. Para evitar que procesos locales no autorizados tomen el control, cada conexión requiere una validación de token autenticada ejecutada en tiempo constante: 

// Desde crates/automation/src/security.rs (Líneas 96-101):
/// Compara tokens de ancho fijo sin salida anticipada al encontrar un byte distinto.
pub fn token_matches(expected: &str, supplied: &str) -> bool {
    if expected.len() != TOKEN_HEX_LEN || supplied.len() != TOKEN_HEX_LEN {
        return false;
    }
    expected.bytes().zip(supplied.bytes()).fold(0u8, |different, (a, b)| different | (a ^ b)) == 0
}

Por qué es seguro: Una comparación común de cadenas de texto (==) se interrumpe al encontrar el primer byte diferente, filtrando información de tiempo que permitiría a un atacante local adivinar el token byte por byte[cite: 2]. PhotoCraft realiza operaciones XOR acumulativas a lo largo de los 64 caracteres hexadecimales, garantizando un tiempo de ejecución constante[cite: 2].

4. Aislamiento de Directorios Basado en Capacidades (`crates/automation/src/workspace.rs`)

Cuando un cliente de automatización solicita lectura o escritura de archivos, las rutas no se resuelven de forma global[cite: 2]. En su lugar, PhotoCraft emplea descriptores de archivos basados en capacidades (cap-std) y limpia estrictamente las rutas relativas[cite: 2]: 

// Desde crates/automation/src/workspace.rs (Líneas 145-163):
for component in raw.split('/') {
    if component.is_empty() { return Err(path_error(raw, "no se permiten componentes de ruta vacíos")); }
    if component == "." { return Err(path_error(raw, "no se permite el componente de ruta `.`")); }
    if component == ".." { return Err(path_error(raw, "no se permite la navegación hacia el directorio padre")); }
    if component.ends_with(['.', ' ']) { return Err(path_error(raw, "no se permiten componentes de ruta que terminen en punto o espacio")); }
    if is_windows_device_name(component) { return Err(path_error(raw, "no se permiten nombres de dispositivos reservados")); }
}

Por qué es seguro: Esto deniega técnicas clásicas de salto de directorio (../../etc/passwd), nombres reservados de Windows (CON, NUL, AUX) y separadores de barra invertida[cite: 2]. Todas las operaciones de entrada/salida ocurren exclusivamente a través del descriptor del directorio asignado, evitando ataques de escape por enlaces simbólicos[cite: 2].

5. Pruebas Fuzzing de Entrada Adversaria ("Sin Bloqueos" y `panic_hunt`)

El código de producción tiene prohibido mediante clippy el uso de unwrap(), expect() y panic![cite: 2]. Para garantizar que entradas maliciosas nunca detengan la aplicación ni corrompan el trabajo del usuario, PhotoCraft incluye una prueba de integración defensiva dedicada: 

// Desde crates/engine/tests/panic_hunt.rs (Líneas 40-56):
let params: Vec<Value> = vec![
    json!({}),
    json!({"x": -9, "y": -9, "radius": 0, "amount": 0, "angle": 0, "opacity": 0, "scale": 0, "levels": 0, "tolerance": 0, "gamma": 0, "layer": 999999, "channel": 999, "index": 999999, "count": 0}),
    json!({"x": 1e5, "y": -1e5, "radius": 300, "amount": 300, "angle": 1e5, "opacity": -100, "scale": -5, "gamma": -1}),
    json!({"points": [], "from": [0, 0], "to": [0, 0], "stops": [], "matrix": [0, 0, 0, 0, 0, 0], "colors": [], "name": "", "mode": "", "style": ""}),
];
for spec in command_specs() {
    for p in &params {
        if let Err(why) = run_guarded(spec.id, p) {
            bad.push(format!("{} [{why}] <- {p}", spec.id));
        }
    }
}

Por qué es seguro: Los aproximadamente 700 comandos del motor son evaluados sistemáticamente con límites anómalos, campos faltantes, índices de capa fuera de rango y valores flotantes extremos[cite: 2]. Se verifica que cada comando devuelva una respuesta de error controlada (Err) sin generar fallos catastróficos ni bloquear hilos de trabajo[cite: 2].

SECCIÓN 4: PUNTOS DESTACADOS EN ARQUITECTURA Y RENDIMIENTO

Además de la ingeniería de seguridad defensiva, PhotoCraft demuestra una arquitectura de software ejemplar[cite: 2]:

  • Almacenamiento de Teselas de 256×256 con Copy-on-Write: Los datos de píxeles se almacenan en teselas dispersas direccionadas por contenido detrás de Arc<Tile<F>>[cite: 2]. Las capturas de estado del documento tienen una complejidad de $O(\text{capas})$ en lugar de $O(\text{píxeles})$, lo que permite operaciones de deshacer/rehacer instantáneas, lecturas no bloqueantes de la interfaz gráfica y guardado automático en segundo plano mediante arc-swap sin duplicar memoria[cite: 2].
  • Desacoplamiento Estricto por Capas: Verificado mediante cargo xtask layers en integración continua[cite: 2]. El motor es 100% independiente de la biblioteca de interfaz de usuario; el frontal en egui actúa solo como una capa de visualización, enviando cada acción del usuario mediante identificadores de comando tipados (filter.blur.gaussianBlur)[cite: 2].
  • Gestión Completa de Profundidad de Color y Perfiles ICC: A diferencia de proyectos tradicionales que dependían de teselas RGB de 8 bits, PhotoCraft soporta múltiples profundidades de bits (8, 16, 32f) y modos de color (RGB, Escala de grises, CMYK, Lab) desde su concepción[cite: 2]. La combinación de capas opera mediante un motor ICC nativo en Rust (photocraft-cms), y los sombreadores GPU se validan contra el motor de composición en CPU con una precisión de ≤ 1/255[cite: 2].
  • Automatización Orientada a Entornos Sin Interfaz (Headless): Todas las herramientas, ajustes y opciones de menú están expuestas a través de la interfaz de línea de comandos y el protocolo MCP, lo que permite flujos de trabajo con agentes de IA, procesamiento masivo y verificación automatizada sin requerir un servidor gráfico[cite: 2].
SECCIÓN 5: RECOMENDACIONES PARA EL FUTURO
  1. Fuzzing Continuo Programado: Aunque existen objetivos de fuzzing en crates/*/fuzz, su integración en canalizaciones continuas de OSS-Fuzz / ClusterFuzz asegurará la protección contra regresiones en nuevos módulos de formato[cite: 2].
  2. Transporte Local Cifrado: El canal de control TCP en bucle local utiliza JSON en texto plano sobre 127.0.0.1[cite: 2]. Aunque está protegido por un token de 256 bits, migrar a sockets de dominio Unix con verificación de credenciales (SO_PEERCRED) en sistemas Unix, o TLS local, mitigará la intercepción en estaciones de trabajo con múltiples usuarios[cite: 2].
  3. Permisos Granulares en Automatización: Evolucionar la autenticación basada en tokens hacia sesiones con permisos delimitados (por ejemplo, permitir inspección de solo lectura sin autorización para guardar documentos)[cite: 2].
  4. Trazabilidad de Publicación y SBOM: Generar una lista de materiales de software (SBOM en formato SPDX/CycloneDX) legible por máquinas y firmar criptográficamente los paquetes de entrega mediante Sigstore/cosign en la canalización automatizada de publicaciones[cite: 2].
